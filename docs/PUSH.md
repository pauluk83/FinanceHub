# Web push — build, deploy and verify

Decided 2026-11-20: the sender runs as a **Supabase Edge Function**, so the VAPID
private key is a Supabase secret beside auth and the backup bucket. The code is
finished and tested; **nothing has been delivered to a real device yet**, because
deployment needs one owner step (`npx supabase login`).

## What ships

| Piece | Where | Notes |
| --- | --- | --- |
| Alert choice | `core/push.ts` and `supabase/functions/send-push/_shared/alerts.ts` | Bills, balances, cards and category targets at warning or critical, three at most, critical first |
| Encryption and VAPID | `supabase/functions/send-push/_shared/webpush.ts` | RFC 8291 `aes128gcm` and RFC 8292 ES256, proven against the RFC 8291 Appendix A vector |
| Sender | `supabase/functions/send-push/index.ts` | Verifies the caller's JWT with Supabase, scopes every row by that user id, records each alert once |
| Subscription table | `db/migrations/postgres/0006_push_subscriptions.sql` | `push_subscriptions` and `push_deliveries`, RLS owner-only, never applied automatically |
| Browser subscription | `app/src/push.ts`, `app/public/sw.js` | Permission prompt, `pushManager.subscribe`, `push` and `notificationclick` handlers |
| Public key | `app/src/pushConfig.ts` | The public half of the pair; safe to publish, overridable with `VITE_VAPID_PUBLIC_KEY` |
| Key pair | `tmp/vapid-keys.json` | Generated by `node scripts/vapid-keys.mjs`; gitignored, owner-only |

The app derives the alert with its own engine and hands it to the sender. The
sender stores the alert id and date in `push_deliveries`, so the same alert is
never pushed twice, and it never computes a figure of its own.

## Owner steps

1. **Apply the table migration.** Supabase → SQL Editor → run all of
   `db/migrations/postgres/0006_push_subscriptions.sql`. It is written with
   `create table if not exists` and `drop policy if exists`, so re-running is safe.
2. **Authorise the CLI once:** `npx supabase login` (browser OAuth, stored outside
   the repository).
3. **Set the secrets** without ever printing the private key:

   ```bash
   npx supabase secrets set --project-ref fzkkgbatmmgasfmgvrzp \
     VAPID_PUBLIC_KEY="$(node -p "require('./tmp/vapid-keys.json').publicKey")" \
     VAPID_PRIVATE_KEY="$(node -p "require('./tmp/vapid-keys.json').privateKey")" \
     VAPID_SUBJECT="$(node -p "require('./tmp/vapid-keys.json').subject")"
   ```

   `APP_ORIGINS` is optional; it defaults to `https://financehub-uk.pages.dev`,
   `http://localhost:5173` and `http://127.0.0.1:5173`.

4. **Deploy the function:**

   ```bash
   npx supabase functions deploy send-push --project-ref fzkkgbatmmgasfmgvrzp
   ```

`SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are supplied
to the function by Supabase; never copy them into the app, a build or this repo.

## Verify

1. Open <https://financehub-uk.pages.dev/>, sign in, and go to **Notifications**.
2. **Turn on push** — allow the browser prompt. The badge reads *On for this device*.
3. **Send a test push** — a notification titled *FinanceHub push is on* arrives.
   Close the tab before pressing it to prove the service worker alone shows it.
4. Re-open the app with a warning alert present (a bill due in the next week).
   One push arrives; a second load pushes nothing, because the alert is recorded.
5. **Turn off on this device** — the subscription is removed from
   `push_subscriptions` and `pushManager.getSubscription()` returns nothing. It
   receives no further push.
6. Check `push_deliveries` has one row per pushed alert and **no title, detail or
   amount**: only `user_id`, `alert_id` and `sent_on`.

## Limits and decisions

- Delivery is triggered by the app deriving its alerts (on load and after a save),
  not by a server-side cron, because the budget is only ever read by the app.
  A phone that never opens the app gets no push; the daily email digest is the
  backstop for that.
- The Windows app has no service worker or push permission, so the section reads
  *Not available here* there and the in-app bell is the only alert.
- Browsers only allow push on a secure origin, so this works on the Pages origin
  and on `localhost`, not on a plain-HTTP LAN address.
- Regenerating the pair (`node scripts/vapid-keys.mjs --force`) invalidates every
  existing subscription: update `app/src/pushConfig.ts`, redeploy, and every
  device must turn push on again.
- Push subscription endpoints and keys are personal data in the processor
  register (Supabase, P1). Record the Edge Function and VAPID secret there before
  relying on it beyond private use.
